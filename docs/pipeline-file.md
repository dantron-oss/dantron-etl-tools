# The pipeline file

Every key a pipeline file may hold, what it means, and the YAML traps that catch people. The key
tables are generated from the loader, so they list exactly what it accepts. A key not listed here
is refused when the file loads, with the nearest correct name suggested.

## A whole file

```yaml
name: Paid sales by region

lanes:
  - {id: sources, title: "What we read", order: 0}
  - {id: figures, title: "The figures", order: 1}

containers:
  - {id: read_inputs, title: "Read the orders and the customer list"}

steps:
  - id: orders
    tool: read_csv
    lane: sources
    container: read_inputs
    why: Every order, as the shop's system exported it.
    config:
      path: pipelines/sales/orders.csv

  - id: customers
    tool: read_csv
    lane: sources
    container: read_inputs
    why: Who each customer is and which region they are in.
    config:
      path: pipelines/sales/customers.csv

  - id: with_customer
    tool: join
    lane: figures
    stage: match
    why: Each order with its customer's region.
    config:
      keys: [customer_id]
    inputs: {left: orders.rows, right: customers.rows}

  - id: every_order_has_a_customer
    tool: assert_rows
    lane: figures
    stage: check
    why: An order for a customer we do not know is a gap in the customer list. Stop and say so.
    config:
      label: every order names a known customer
      predicate: "false"
      allow_empty: true
    inputs: {rows: with_customer.left_only}

  - id: by_region
    tool: group_by
    lane: figures
    stage: totals
    why: One row per region.
    config:
      by: [region]
      aggregations:
        - {name: total, function: sum, value: "[amount]"}
    inputs: {rows: with_customer.joined}

  - id: save
    tool: write_csv
    lane: figures
    why: The totals as a file.
    config:
      path: output/by_region.csv
      overwrite: true
    inputs: {rows: by_region.rows}
```

The check step is a pattern worth knowing. `left_only` should be empty, so the step asserts
`false`, which no row passes, and allows the port to be empty. Any order that reaches it stops the
run, and the message shows the first one.

## Inputs

`inputs` maps each of the tool's input ports to an output of an earlier step, written `step.port`:

```yaml fragment
inputs:
  left: paid.true
  right: customers.rows
```

`{left: paid.true, right: customers.rows}` on one line means the same. A step id may not contain a
dot, because the text is split at the first dot. A tool that reads nothing, such as `read_csv`, has
no `inputs`. `dantron-etl help <tool>` lists a tool's ports under "Reads" and "Gives".

Steps may be written in any order; the run order comes from the wiring. A loop in the wiring is
refused.

## Rules

`${rules.name}` in any setting is replaced by the rule's value before the pipeline is checked. The
values come from the project file, `etl-project.yaml`, under the pipeline's name:

```yaml fragment
pipelines:
  sales:
    rules: {status: PAID, start: 2025-01-01}     # written here
  month_end:
    rules_file: config/month_end.yaml            # or read from a file
  ledger:
    rules_loader: my_project.rules:load          # or returned by a function in your project
```

A rules file holds `name: value` lines, or `name: {value: ..., why: ...}` to say why a value was
chosen; one form per file. A `rules_loader` runs your project's own Python code, and only when the
pipeline is checked or run, never when the viewer lists the project.

How the value is put in depends on the setting:

- **In an expression setting** (`filter`'s `predicate`, `formula`'s `value`, and the others a tool's
  help marks `expression`), the value is quoted and escaped for you. `[code] = ${rules.code}` and
  `[code] = '${rules.code}'` both match the rule's value exactly, apostrophes and all. Write
  `date'${rules.start}'` for a date. A number stays a number.
- **In any other setting** (a path, a pattern, a sheet name, a column name), the value is put in as
  it is, with nothing added: `path: "output/${rules.region}.csv"`.
- **A reference that is the whole setting** takes the value with its type: a list stays a list.
- **A true/false or empty rule cannot go inside quotes.** YAML reads `wanted: no` in a rules file as
  false, not as text. Quote the value in the rules file if you mean the text.

A rule the pipeline uses and nobody set is refused when the file loads, with the lines to add.

## Paths

Through the command, a relative `path` is read from the project folder, wherever you run the
command from. From Python, it is read from the working folder, unless you pass
`run_pipeline(spec, base_dir=project_folder)`.

A file writer is checked when the file loads: its folder must exist, and a file already there is
refused unless the step says `overwrite: true`. A pipeline that runs every night needs
`overwrite: true` from the first night.

## YAML traps

YAML is forgiving in ways that change what you wrote. These are the ones that bite.

- **Some bare words are not text.** `true`, `false`, `yes`, `no`, `on`, `off`, `null` and `~` (in any
  case) become true, false or empty. `on: [id]` becomes the key `True`. No setting or allowed value
  in this library uses those words. If one of your own values is such a word, quote it: `'no'`.
- **A colon followed by a space ends a plain value.** `why: The month becomes text, for one reason: a
  heading is text.` does not load. Use `>` and put the text on the next lines:

  ```yaml fragment
  why: >
    The month becomes text, for one reason: a heading is text.
  ```

- **Quote every expression.** `predicate: [status] = 'PAID'` starts with `[`, which YAML reads as a
  list. Write `predicate: "[status] = 'PAID'"`. Single quotes go inside, double quotes outside.
- **Backslashes depend on the quotes.** In double quotes, `"\\d"` becomes `\d`, which is what a
  pattern wants. In `>` or `|` text, `\\d` stays two backslashes and matches nothing, with no error.
  Put patterns in double quotes.
- **A comma ends a value inside `{ }`.** `{from: total, to: Total, all customers}` is three entries,
  and the third key is `all customers`. Quote a value with a comma in it: `to: "Total, all
  customers"`.
- **A `#` starts a comment in YAML, but not in an expression.** Inside a quoted expression `#` is
  refused. Put notes in the step's `why`.
- **Indentation is structure.** Use spaces, never tabs, and keep a step's keys lined up under its
  `id`.

## The project file

`etl-project.yaml` sits at the top of a project. Every key is optional.

<!-- project keys: generated by docs/_build/generate.py; do not edit by hand -->

| key | what it is |
|---|---|
| `pipeline_folders` | Folders holding pipeline files. Default `[pipelines]`. |
| `runs_folder` | Where runs are saved for the viewer. Default `output_files/runs`. |
| `pipelines` | Settings for each pipeline, under its name (the file name without `.yaml`). |
| `rules` | Under a pipeline: the values its `${rules.name}` references take. |
| `rules_file` | Under a pipeline: a YAML file of rule values, relative to the project folder. |
| `rules_loader` | Under a pipeline: `module:function` in your project that returns the rule values. |
| `focus` | Under a pipeline: the column, or list of columns, the viewer lets you follow. |

<!-- project keys: end -->

An older layout, `pipelines/<name>/settings.yaml` holding `rules` and `focus`, still works.

## A file from an older version

A pipeline written for an earlier version may use names that have since changed. The loader
refuses it and says what each old name is called now. `dantron-etl migrate` rewrites the file. See
[Upgrading](upgrading.md).
