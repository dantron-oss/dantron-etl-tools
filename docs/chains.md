# Chains: running several pipelines in order

A **chain** runs several pipelines in order. The ones that need another's output run after it, and
the ones that do not need each other run side by side. A chain is a short YAML file in the
project's `chains/` folder. Each pipeline in it stays an ordinary pipeline: it still runs, previews
and opens in the viewer on its own.

```yaml chain
# chains/month_end.yaml
title: Month-end close

parameters:
  period: "2026-11"          # the default; change it for one run with --set period=2026-12

pipelines:
  - name: load_ledger
  - name: load_customers
  - name: clean_ledger
    after: [load_ledger]
  - name: clean_customers
    after: [load_customers]
  - name: revenue
    after: [clean_ledger, clean_customers]
```

`load_ledger` and `load_customers` start together. `clean_ledger` starts when `load_ledger` has
finished. `revenue` starts when both cleans have finished.

Pipelines pass data to each other the way they do today: one writes a file or a table and the next
reads it. Nothing is passed in memory, so every hand-off stays on disk where you can open it.

## Making a chain from pipelines you already have

`chain suggest` works the order out from what each pipeline reads and writes, and writes a first
chain file for you to read:

```bash
dantron-etl chain suggest month_end load_ledger load_customers clean_ledger clean_customers revenue
```

Leave the pipeline names out to put every pipeline of the project in it. Add
`--set period=2026-11` for a value the pipelines take from the chain. `--print` shows the file
instead of writing it. The file says beside each `after` which files and tables pass along it, and
lists rules that more than one pipeline uses, which you may want as parameters.

It never overwrites a chain file that is already there.

## The chain file

**Top level of the file**

| key |  | what it is |
|---|---|---|
| `title` | optional | The chain's title, shown in the viewer. Default: the file's name. |
| `parameters` | optional | Values shared by the whole chain, one `name: default` line each. Each is handed to every pipeline that writes `${rules.name}`, in place of its own value. Change one for a run with `--set`. |
| `max_parallel` | optional | How many pipelines may run at the same moment. Default 2. |
| `pipelines` | required | The pipelines the chain runs, one entry each, in any order. |

**Each entry under `pipelines`**

| key |  | what it is |
|---|---|---|
| `name` | required | The pipeline's name, as the project lists it. |
| `after` | optional | The pipelines that must finish before this one starts: `after: [load, clean]`. |
| `why` | optional | A sentence saying why it is in the chain. Shown nowhere else; it is for the reader of the file. |

<!-- chain keys: end -->

An entry can be just the pipeline's name, `- load_ledger`, when it runs after nothing.

A chain cannot have the name of a pipeline, because both are run by name. The folder can be
changed with `chain_folders` in `etl-project.yaml`.

## The order is checked against the files and tables

Before anything runs, the library loads every pipeline in the chain and works out each file and
table it reads and writes. The chain is refused, naming the pipeline, the file and the fix, when:

- a pipeline reads a file or table another pipeline in the chain writes, but does not run after it.
  Without this check the two could run at the same time, and the reader would take what an earlier
  run left there. Running after the writer by way of another pipeline is enough.
- a pipeline runs before the one that writes what it reads (the order is backwards).
- two pipelines write the same file or table.
- the pipelines wait for each other in a loop.
- a pipeline is not in the project or does not load.

Every disagreement is listed at once. A file is matched by its full path, after rules are filled in.
A table is matched by its connection's environment variable name, its schema and its name, without
regard to capitals; a table written without a schema matches the same table in any schema. Two
different variable names that point at the same database are not seen as the same database.

Running after a pipeline that writes nothing you read is allowed: the order may matter for a reason
the files do not show. The viewer draws that line dashed.

## Parameters

A parameter is a value the whole chain shares, such as the period. Each one is handed to every
pipeline in the chain that writes `${rules.<name>}`, in place of the value the pipeline's own settings
give, and only for that run.

- Change one for a run: `dantron-etl run month_end --set period=2026-12`.
- The value given is read as the same kind as the default: a date where the default is a date, a
  number where it is a number, text where it is text. A value of another kind is refused.
- A parameter no pipeline uses is refused, so a misspelt name cannot quietly do nothing.
- The plan says which pipelines use each value, and which own setting it replaces.
- Each pipeline's saved run records the chain and the values it was given.

## Running a chain

```bash
dantron-etl run month_end                       # check it and print the plan; nothing runs
dantron-etl run month_end --write               # list every write, ask for the name, run for real
dantron-etl run month_end --write --set period=2026-12
dantron-etl run month_end --write --from clean_ledger    # that pipeline and everything after it
dantron-etl run month_end --write --until clean_ledger   # that pipeline and everything before it
dantron-etl check chains/month_end.yaml         # the same check, for a chain file
```

Without `--write` it checks the chain and prints the order, the values, what passes between the
pipelines, what comes from outside the chain and what it leaves behind. Nothing runs.

With `--write` it also lists every file and table each pipeline will write, and asks you to type the
chain's name. If a pipeline, the chain file or a value changes between being shown and being run,
the run is refused and nothing runs. `--yes` skips the question, for scheduled jobs.

**When a pipeline fails**, every pipeline that waits for it, however far on, is not started. The
pipelines that do not depend on it carry on, because their figures do not depend on the failure.
The run ends as failed and lists what did not start. The files and tables those pipelines write
still hold what an earlier run left there.

### How many run at once: `max_parallel`

The chain decides *which* pipelines run and in what order. `max_parallel` decides only *how many run
at the same moment*. Say ten pipelines are all waiting on `load_sources`. When it finishes, all ten
may start. With `max_parallel: 2`, two start, and each time one finishes the next one starts. All
ten still run, and the figures are the same whatever the setting. Only the time the run takes and
the load on the computer change.

The default is **2**. Each running pipeline holds its data in memory, so ten at once can need ten
times the memory of one. A computer that runs out of memory does not refuse the run cleanly: the
pipeline is stopped partway, possibly after other pipelines have already written their files. Running
many at once also gains less than it seems, because each pipeline already uses every core of the
computer.

- Raise it, `max_parallel: 4`, when your pipelines are small.
- Lower it to 1 when one of them is large.
- Under Prefect it is not used: see below.

Each pipeline runs in a process of its own, so the memory it held is given back when it ends. If the
system stops one, that pipeline is reported as failed with a note about memory, and the others carry on.

## In the viewer

The viewer lists chains below the pipelines. A chain's page draws one box per pipeline and one line
per `after`. Each line says which file or table passes along it, or "order only". The page shows no
rows: click a box to open that pipeline's own page, where its steps and rows are. Opening the page
runs nothing.

After a chain has run, each box says how its pipeline did in the chain's latest run: finished,
failed, or not started because something before it failed. The page also shows the parameters, the
latest run, what passes between the pipelines, and what comes from and goes outside the chain. When
a pipeline has been run again since, on its own, the page says so.

## What is saved

Each pipeline's run is saved exactly as when it runs alone, so the viewer shows its steps and rows.
The chain's own run is saved as a small file in `<runs folder>/<chain>.chain/`: when it ran, the
values, and how each pipeline did. It holds no rows.

## Running a chain under Prefect

The library does not depend on Prefect. Copy this file into your project, next to
`etl-project.yaml`, and change `CHAIN` to your chain's name. One flow runs the chain, and each
pipeline is a task of its own.

```python
"""Run a chain under Prefect: one flow for the chain, one task for each pipeline."""

from pathlib import Path
from typing import Any

from prefect import flow, get_run_logger, task
from prefect.task_runners import ThreadPoolTaskRunner

from dantron_etl.chains import load_chain, run_member

ROOT = Path(__file__).resolve().parent  # the project folder
CHAIN = "month_end"


@task
def run_pipeline(pipeline: str, parameters: dict[str, Any]) -> str:
    record = run_member(ROOT, CHAIN, pipeline, parameters, logger=get_run_logger())
    if record.outcome != "finished":
        raise RuntimeError(f"{pipeline} {record.outcome}: {record.message}")
    return record.outcome


@flow(name=CHAIN, task_runner=ThreadPoolTaskRunner(max_workers=2))
def run_chain(parameters: dict[str, Any] | None = None) -> list[Any]:
    parameters = parameters or {}
    plan = load_chain(ROOT, CHAIN, parameters)  # the whole check, before anything runs
    started: dict[str, Any] = {}
    for name in plan.order:
        started[name] = run_pipeline.with_options(task_run_name=name).submit(
            name, parameters, wait_for=[started[before] for before in plan.after(name)]
        )
    return list(started.values())


if __name__ == "__main__":
    run_chain()
```

| in a chain | in Prefect |
|---|---|
| the chain | a flow |
| a pipeline in it | a task run, named after the pipeline |
| `after` | `wait_for` |
| parameters | the flow's `parameters`, for example `{"period": "2026-12"}` |
| a failed pipeline | a failed task; the tasks waiting on it do not run (Prefect shows them as `NotReady`), the others carry on, and the flow ends as failed |
| each step's message | Prefect's run log |
| `max_parallel` | the task runner's `max_workers` (2 above) |

This recipe was run under Prefect 3.9, with a chain that finished and with one where a pipeline failed.
The flow reads the chain file each time it runs, so a change to the chain needs no change here.
Each pipeline's run is saved in the project as usual, so the viewer shows it. Scheduling, retries
and alerts are Prefect's: set them on the deployment. A retry of a pipeline that failed on its data
will fail again.

## From Python

```python
from dantron_etl.chains import load_chain, run_chain

plan = load_chain("path/to/project", "month_end", {"period": "2026-12"})
print(plan.order, [(h.writer, h.target.shown, h.reader) for h in plan.handoffs])
result = run_chain("path/to/project", "month_end", parameters={"period": "2026-12"}, confirm_digest=plan.digest)
print(result.outcome, [(m.pipeline, m.outcome) for m in result.members])
```

`run_member` runs one pipeline of a chain with the chain's values, for a scheduler that runs each as
its own task. `suggest_chain` gives the text `chain suggest` writes.

## What a chain does not do

- It does not pass data between pipelines in memory.
- It does not schedule. Running at six in the morning is the scheduler's job.
- No chain inside a chain, no "run B only if A wrote rows", no loop over a list of values.
- It never reshapes data. It runs pipelines, saves what they did, and draws them.

Why it works this way: [design notes](design/chains.md).
